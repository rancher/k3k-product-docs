= Creating Etcd Snapshots of a Virtual Cluster
:description: Create local or S3-uploaded etcd snapshots of the datastore of a Kubernetes virtual cluster using the EtcdSnapshot custom resource
:revdate: 2026-11-23
:page-revdate: {revdate}

{k3k-product-name} can trigger an etcd snapshot of the datastore of a virtual cluster on demand when you create an `EtcdSnapshot` resource. The K3s server of the virtual cluster takes the snapshot with the link:https://docs.k3s.io/cli/etcd-snapshot[K3s etcd-snapshot feature]. The snapshot is stored on the local disk of the server, or uploaded to an S3-compatible object store.

To restore a virtual cluster from a snapshot, see xref:how-tos-for-admin/etcd-restore.adoc[Restoring a Virtual Cluster from an Etcd Snapshot].

[IMPORTANT]
.Snapshots require the embedded datastore
====
Snapshots are only supported for virtual clusters that use the default embedded datastore. Clusters configured with an xref:how-tos-for-admin/external-datastore.adoc[external datastore] do not run an embedded etcd and do not support snapshots.
====

== Prerequisites

* A virtual cluster in the `Ready` phase. The snapshot controller requeues the request until the target cluster becomes ready.
* For S3 uploads, an S3-compatible bucket and credentials.

[#_create_a_local_snapshot]
== Create a local snapshot

. Create a manifest file named `my-cluster-snapshot.yaml` with an `EtcdSnapshot` resource that references the target cluster by name:
+
[source,yaml]
----
apiVersion: k3k.io/v1beta1
kind: EtcdSnapshot
metadata:
  name: my-cluster-snapshot
  namespace: test-k3k
spec:
  clusterRef:
    name: my-cluster
  compress: true # optional, compresses the snapshot file
----
+
The `compress` field is optional and defaults to `false`.

. Apply the manifest. The snapshot is saved to the local disk of the server:
+
[source,bash]
----
kubectl apply --filename my-cluster-snapshot.yaml
----

The `clusterRef`, `s3ConfigSecretRef` and `compress` fields are immutable after the `EtcdSnapshot` is created. To change any of these values, delete the resource and create a new one.

[#_create_an_s3_snapshot]
== Create an S3 snapshot

To also upload the snapshot to an S3-compatible bucket, create a `Secret` with the S3 connection details and reference it from the `EtcdSnapshot`.

The keys of the secret match the link:https://docs.k3s.io/cli/etcd-snapshot#s3-compatible-object-store-support[K3s S3 configuration options]:

[cols="30a,70a", options="header"]
|===
| Key | Description
| `etcd-s3-endpoint` | S3 endpoint. Required unless you use the default `s3.amazonaws.com` endpoint.
| `etcd-s3-access-key` | S3 access key.
| `etcd-s3-secret-key` | S3 secret key.
| `etcd-s3-bucket` | S3 bucket name.
| `etcd-s3-folder` | Folder or prefix inside the bucket.
| `etcd-s3-region` | S3 region.
| `etcd-s3-bucket-lookup-type` | S3 bucket lookup type, for example `path`.
| `etcd-s3-proxy` | Proxy server to use when connecting to S3.
| `etcd-s3-session-token` | S3 session token.
| `etcd-s3-timeout` | Timeout for S3 operations, for example `5m`.
| `etcd-s3-retention` | Number of snapshots to retain in S3.
| `etcd-s3-insecure` | Set to `"true"` to use plain HTTP instead of HTTPS.
| `etcd-s3-skip-ssl-verify` | Set to `"true"` to skip TLS certificate verification.
| `etcd-s3-endpoint-ca` | Inline PEM-encoded CA bundle for the S3 endpoint.
| `etcd-s3-endpoint-ca-name` | Name of a `ConfigMap` that contains CA bundles for the S3 endpoint. The `ConfigMap` must be in the same namespace as the secret.
|===

. Create a manifest file named `etcd-s3-config.yaml` with a `Secret` in the same namespace as the `EtcdSnapshot`:
+
[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: etcd-s3-config
  namespace: test-k3k
type: Opaque
stringData:
  etcd-s3-endpoint: s3.example.com
  etcd-s3-access-key: AKIAEXAMPLE
  etcd-s3-secret-key: supersecret
  etcd-s3-bucket: k3k-etcd-snapshots
  etcd-s3-folder: my-cluster
  etcd-s3-region: us-east-1
----

. Create a manifest file named `my-cluster-s3-snapshot.yaml` with an `EtcdSnapshot` resource that references the secret in `spec.s3ConfigSecretRef`:
+
[source,yaml]
----
apiVersion: k3k.io/v1beta1
kind: EtcdSnapshot
metadata:
  name: my-cluster-s3-snapshot
  namespace: test-k3k
spec:
  clusterRef:
    name: my-cluster
  s3ConfigSecretRef:
    name: etcd-s3-config
----

. Apply both manifests:
+
[source,bash]
----
kubectl apply --filename etcd-s3-config.yaml --filename my-cluster-s3-snapshot.yaml
----

[NOTE]
.Lookup of the S3 secret
====
`s3ConfigSecretRef` only looks up the secret by `name`, always in the same namespace as the `EtcdSnapshot`. Any `namespace` set on `s3ConfigSecretRef` is ignored.

Setting `s3ConfigSecretRef` also creates a local snapshot on disk before the upload to S3.
====

[#_verification]
== Verification

* Check the `EtcdSnapshot` status for the generated snapshot file name and the `Ready` condition:
+
[source,bash]
----
kubectl get etcdsnapshot my-cluster-snapshot --namespace test-k3k --output yaml
----
+
[source,yaml]
----
status:
  filename: etcd-snapshot-my-cluster-server-0-1234567890
  conditions:
  - type: Ready
    status: "True"
    reason: SuccessfulCreate
    message: Snapshot was created
----

* A `kubectl get etcdsnapshots` also shows the `FILE NAME` column once the snapshot is created. If the snapshot fails, the `Ready` condition is set to `False` with reason `FailedCreate` and a message describing the error.

[#_delete_a_snapshot]
== Delete a snapshot

Deleting the `EtcdSnapshot` resource removes the underlying snapshot file from the virtual cluster. If an S3 bucket is configured, the snapshot file is also removed from the bucket:

[source,bash]
----
kubectl delete etcdsnapshot my-cluster-snapshot --namespace test-k3k
----

The `EtcdSnapshot` custom resource definition is annotated with `helm.sh/resource-policy=keep`. Uninstalling the {k3k-product-name} Helm chart does not delete the custom resource definition, so existing `EtcdSnapshot` resources are kept.
